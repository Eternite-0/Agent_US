## 1. 真实执行链路

本轮在既有 DirectAgentRuntime、DurableJobQueue、RecoveryWorker、AdaptiveSwarmOrchestrator、Tool Runtime 与 Store 上做增量接入，没有创建第二套 Agent Loop。当前已经验证的链路是：

- Evaluation API / service 创建 synthetic evaluation run，任务在临时目录生成 fixture。
- Evaluation 可通过 DurableJobQueue 写入 `runtime_jobs`，由 RecoveryWorker 的 `evaluation_run` handler 执行；若注入队列明确返回 `null`，服务走受控本地回退以避免永久 `queued`。
- DirectAgent adapter 使用现有 `createSession()` / `startTurn()` / `cancelTurn()`，并在取消、超时或关闭时等待 `waitForTurnTerminal()`；Runner 在无法确认 drain 时保留 workspace。
- Planner 计划经 `validatePlan()` 后映射为既有 durable swarm nodes，`planVersion` 与计划数据进入现有 Swarm 持久化路径。
- CommunicationBus 使用持久化 Store adapter、delivery token 与原子 claim；Memory 使用独立的 Experience Memory 表并向 ContextAssembler 注入项目范围经验。

## 2. 本轮真正完成的改动

### Evaluation Durable

- `backend/src/evaluation/service.js`
  - DirectAgent runtime adapter 返回可 drain 的 runtime handle。
  - worker handler 注册后主动 wake 已启动 RecoveryWorker。
  - queue enqueue 返回空值时受控回退，避免 run 永久停留在 `queued`。
  - `cancel()` 正确识别 `timeout` 终态。
  - `close()` 取消 queued/running evaluation，取消对应 durable jobs，并等待 active execution。
  - 数据库已关闭时 close 直接返回，避免 teardown 误报。
- `backend/test/evaluation/service.test.js`
  - enqueue unavailable fallback。
  - worker registration wake + execution。
  - close → abort → runtime drain → cancelled result。

## 3. 各系统审计结论

| 系统 | 结论 | 真实边界 |
|---|---|---|
| Observability | 已复用既有 synthetic provenance 与 KPI 隔离 | 本轮未扩展新的 KPI 字段 |
| Evaluation | **部分 durable、可真实调用 DirectAgentRuntime** | 仍使用通用 `records` 保存 run，尚未拆分 task/attempt/checkpoint/artifact 专用表；30 个任务仍是确定性本地 fixture smoke dataset |
| Planner | **已验证 Planner → Durable Swarm** | 完整自主意图分析与模型驱动动态 replan 闭环仍有限 |
| Dynamic Team | **TeamOptimizer 可用且受预算/并发约束** | 未接入 AdaptiveSwarmOrchestrator 的生产 dispatch/reassign；因此不能声称动态团队已完成生产闭环 |
| Communication | **持久化至少一次投递 + fence/ACK/retry** | 仍与 legacy `InterAgentMailbox` 并存，尚未统一所有 Swarm mailbox 路径 |
| Memory | **持久化、项目隔离、验证边界、Context 注入** | Evaluation 结果尚未自动写入 verified memory；schema 仍为 lazy additive 初始化，未新增主 Schema v7 migration |
| Capability | **声明/实测分离，Store 持久化** | Provider catalog 主要仍由现有 AccountPool/legacy provider 路径提供；没有伪造测量分数 |

## 4. API 与持久化范围

- `/v1/evaluations`、`/v1/evaluations/:id`、`/v1/evaluations/:id/cancel`

- 复用 Schema v7 generic `records` 保存 evaluation run 与 capability profile。

- Durable Swarm 使用既有 `swarm_runs`、`swarm_nodes`、`runtime_jobs`。

## 5. Benchmark 与真实成绩

当前 benchmark：`agent-us-deterministic-core`，版本 `1.0.0`，dataset `1.0.0`，30 个本地确定性任务，类别数量为 8/5/5/4/3/3/2。

## 10. 未完成能力与风险

1. Evaluation 仍是“部分 durable”，缺少独立 task/attempt/checkpoint/artifact 表与跨进程恢复验收。
2. 尚未完成 SIGKILL 后 Evaluation run 真实恢复以及已完成任务去重验收。
3. Evaluation → verified Memory 自动闭环未实现。
4. TeamOptimizer 尚未接入 Swarm dispatch/reassign。
5. CommunicationBus 与 legacy InterAgentMailbox 尚未完全统一。
6. Benchmark dataset 仍为 deterministic fixture smoke tasks，不是用户要求的真实多文件软件开发 benchmark。
7. 前端 Evaluation Center 已存在 API/页面基础，但本轮未扩展新的 UI 视觉组件，未完成完整 Inspector/TL 页面。
8. 本轮没有新的双平台 GitHub Actions 结论。

## 11. 下一阶段建议

- 将 Evaluation run/task/attempt/checkpoint/artifact/budget/judge 记录建成专用 durable 表或明确的版本化记录协议。
- 为 Evaluation 增加 RecoveryWorker fence、重启、SIGKILL、重复执行保护。
- 在不绕过 Runtime 的前提下，将 TeamOptimizer 选择结果作为 Swarm node dispatch 的输入，并保留替换证据。
- 统一 CommunicationBus 与 InterAgentMailbox 的 envelope/ACK/fence 语义。
- 让确定性 verifier 的证据显式驱动 `rememberVerified()`，并增加失败/取消不写入 verified memory 的测试。
- 构建真实多文件软件工程 benchmark，再以独立 verifier、artifact manifest 与 test/build 结果评分。

## 12. 验收结论

2.2.1 本轮已完成安全的增量集成与回归验证，但**尚未达到“全部自主智能系统完成”或“双平台 CI 全绿”验收线**。可以交付的事实是：现有 Runtime 上的 Evaluation durable 入口、Planner→Swarm 映射、Communication fence、Memory context、Capability Store 持久化均有代码和专项测试证据；完整真实 benchmark、Evaluation crash recovery、TeamOptimizer 生产 dispatch、Memory 自动闭环与本轮远端 CI 仍未完成。
