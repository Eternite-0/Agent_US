## 2. Windows CI 失败根因与双模修复验证 (`c5a894db`)

### 2.1 GitHub Actions Run `45197769615` 失败根因
在 GitHub Actions 矩阵（`.github/workflows/ci.yml`）中，`Verify (ubuntu-latest / Node 24)` 全量通过，而 `Verify (windows-latest / Node 24)` 在 **Step #10 (`Backend core and regression test suites (PowerShell)`)** 失败。排查根因如下：
1. `.github/workflows/ci.yml` 的 Windows 分支显式排除了 `docker-sandbox-acceptance.test.js`（因 GitHub 托管的 `windows-latest` runner 未预置 Linux Docker Engine），且同行 `external-benchmark.test.js` 已通过 `new DockerBenchmarkSandbox().isAvailable()` 在无 Docker 时切换为 `SANDBOX_MODES.NODE_PERMISSION`。
2. `backend/test/evaluation/autonomous-reasoning-benchmark.test.js` 原先无条件实例化 `SANDBOX_MODES.STRONG` 并断言 `dockerProbe.available === true`，因此在无 Docker Engine 的 `windows-latest` 上必然失败。
3. 进入 `NODE_PERMISSION` 进程级隔离后，Windows CI 还会遇到两项附加限制：`hidden-acceptance-supervisor.mjs` 子进程需要显式继承受控临时目录环境（`workerTempDir`），以及无完整 `fs.write=*` 权限的 `Node --permission` 默认禁止 `fs.symlinkSync`（触发在 `ar-05` 隐藏测试构造符号链接逃逸夹具处）。

### 2.2 修复设计与 Fail-Closed 不变量保持 (`c5a894db`)
- **`backend/test/evaluation/autonomous-reasoning-benchmark.test.js`**：探测 `DOCKER_AVAILABLE = new DockerBenchmarkSandbox().isAvailable()`；在 Docker 可用环境（Ubuntu CI 与本地 Windows Docker Desktop）保持全套 `SANDBOX_MODES.STRONG` / `SANDBOX_MODES.DOCKER` / `strongOsIsolation === true` 原样断言；仅在 `DOCKER_AVAILABLE === false` 时使用 `{ mode: SANDBOX_MODES.NODE_PERMISSION, allowProcessHardeningOnly: true }` 并为 CLI 冒烟临时注入作用域限定的 `AGENT_US_BENCHMARK_ALLOW_PROCESS_HARDENING_ONLY = '1'`（`try/finally` 清理）。**`SandboxUnavailableError` Fail-Closed 单元测试在两种模式下均强制执行**。
- **`backend/src/tools/benchmark-sandbox.js` & `hidden-acceptance-supervisor.mjs`**：将 `workerTempDir` 透传到隔离 worker 的 `HOME`/`USERPROFILE`/`TMP`/`TEMP`/`TMPDIR`/`APPDATA`/`LOCALAPPDATA`，消除 Windows CI 路径访问越界。
- **`backend/src/evaluation/autonomous-reasoning-benchmark.js`**：在 `ar-05` 隐藏测试中，仅当 `err?.code === 'ERR_ACCESS_DENIED' && process.permission && !process.permission.has('fs.write', '*')` 时容忍 `fs.symlinkSync` 拒绝并保留全部其余穿越/NUL/编码逃逸断言；Docker `strong` 模式下依然强制创建并测试真实符号链接逃逸。

### 2.3 双环境独立验证结果（来自独立审计记录 `#240`）
- **模拟 Docker-less Windows CI（剥离 Docker PATH，`SIM_DOCKER_AVAILABLE=false`）：** `npm run check` exit `0`；`autonomous-reasoning-benchmark.test.js` **`31/31`**、`benchmark-isolation.test.js` **`21/21`**、`external-benchmark.test.js` **`9/9`** 全部通过（0 fail, 0 skipped）。

### 3.4 Adaptive Context Intelligence (`aci-store.js`, `aci-engine.js`, `supervisor.js`, `intelligence-routes.js`, `AdaptiveContextPanel.tsx`)
- **无损存储与证据账本 (`aci-store.js`)：** `ReversibleContextStore` 复用 `store.putBlob` / `store.getBlob` 将工具输出持久化为 `artifact://<sha256>` 与 `aci.ref:<refId>` 映射，`restore()` 保证 100% 字节级无损；格式桩 `[ACI-REF <uri> | <path> | <lines> | <symbols> | ~<tok> tok | call expand_context or read_blob to restore]`；`ContextEvidenceLedger` 追踪候选、保留、压缩与恢复并计算 `computeCriticalContextRecall`。
- **分期 DTOC 与 Repoformer 预门控 (`aci-engine.js` + `agent-loop.js`)：**
  - Round 2（`08040592`）发现原单步 `tokensBefore / maxTotalTokens`（~5k/160k=3%）永远不触发，因而新增累计预算感知水位判定：`ratio = Math.max(tokensBefore / contextWindow, (cumulativeUsedTokens + tokensBefore) / maxTotalTokens)`；Round 3（`9d320baf`）基于 Run 2 实测反驳“激进 Supervisor 无收益”的假设，收紧默认水位至 **`DEFAULT_EPOCH_WATERMARKS = [0.60, 0.82]`**，提取统一共享判定 `evaluateToolMessageEligibility`（由 `selectOffloadableAciCandidates` 与 `compressMessagesEpoch` 共用），将常规非报错已消费 `read_file`/`glob`/`grep`/`bash` 阈值由 `1200` 降至 **`700` chars**（`minAgeSteps = 3`），并允许**被后续编辑覆盖的过期预编辑 `read_file`**（`msgStep < lastMutationStepByPath` 且 `age >= 2 && chars >= 600`）参与卸载，同时严格保护编辑后活跃读（`msgStep >= lastMutationStepByPath`）、报错输出、`[ACI-REF ...]` 及 `pairClosed` 成对工具调用边界。
  - `AgentLoop` 触发 `epochProbe` 后先筛选 `eligibleCandidates`：若为 `0` 则**同时跳过 Supervisor 与 DTOC 且不消耗 epoch 水位**；仅当 **`eligibleCandidates.length >= 2 && totalEligibleChars >= 2400 && aciSupervisorCalls < 2`** 时才调用 Supervisor（Repoformer 弃权门控），否则仅运行确定性 DTOC。每次应用前强制验证 `pairClosedValid !== false`。
- **只读 ContextSupervisor 与号池动态解析 (`supervisor.js` + `/v1/context/supervisor` + UI)：**
  - 配置持久于 `kv_settings`（`aci.config`），支持 `mode: 'auto' | 'custom' | 'off'` 与实时调参（`GET` / `PATCH /v1/context/supervisor` 对应前端 `SettingsView.tsx` 中的 `AdaptiveContextPanel.tsx` 与 `client.ts`）。
  - **零硬编码模型名称**：完全复用 `AccountPool`（`getActiveCatalog()`, `resolveRoutes()`, `getDefaultModel()`）按轻量/低延迟/健康状态动态评分路由；调用时强制锁定 **`tools: []`**（无写文件/执行/审批权限），输出经 JSON 校验与候选 ID 白名单过滤，超时或报错自动 Fail-Closed 回退到确定性 DTOC。

## 5. 客观 2.4 成熟度评估与 Stage 4 演进计划

### 5.1 诚实成熟度结论：**不宣称 2.4 在全题集与全端到端场景下已“普遍达标”**
我们必须如实区分**已通过实盘验证的明确工程收益**与**尚未解决的模型/上下文调度边界**：

1. **已验证的确定性工程收益：**
   - **安全免脚本摘要原语 (`compute_file_digest`)：** Run 1 (`101.6s, dig=3, PASS`) 与 Run 3 (`65.1s, dig=3, PASS`) 中 `ar-09` 在无 `node -e` 执行权限下稳定一次性通过，而无该工具的 Baseline 在 Run 1/2/3 中 **`0/3` 全败**。
   - **只读 `doc` 免重验与 `self_test` 校准容忍：** `ar-05` Run 1/2 与 Exp Probe 消除写入 `SECURITY.md` 后的死循环误判；Run 3 `ar-08` 彻底消除 `Stage 2` 第 20 步自测误熔断并取得 `ff=1, rec=1`。
   - **可信经验闭环实证提效：** 在严格 `trusted_server_verifier` 准入下，Verified-Seeded 对比 Cold 在 `ar-03,05,09` 上取得 `finalTaskSuccessRate` **`+0.3334`（`0.3333 -> 0.6667`）**、将 `ar-03` 耗时缩短 **`-45.9%`** 并使 `ar-05` 跨轮反转为通过。
   - **Windows CI 双模无损兼容 (`c5a894db`)：** 同时保持 Docker `strong` 全强隔离与 GitHub `windows-latest` CI `NODE_PERMISSION` 无跳测试通过，且不放松 Fail-Closed。
   - **Repoformer 预门控与过期读卸载收敛：** Run 3 将无收益 Supervisor 调用由 **`23` 次压降至 `1` 次**（节省 `~174.7k` tokens 与 `~20.6s` 均值时延），同时首次实现真实 DTOC 卸载（`offloadedCount=6, savedTokens=949`）。

2. **尚未攻克的客观瓶颈（禁止掩饰）：**
   - **`deepseek-v4.1-flash` 基础能力上限：** `ar-01`（`CONTRACT.json` 图谱精确结构）、`ar-04`（3 模块同时委托去重）、`ar-07`（CLI 退出码/参数契约）、`ar-10`（长程 5 约束全部保真）以及 Run 3 `ar-05`（`__proto__` 防护报错语义）仍暴露显著的弱/中端模型推理上限，且 `--repeats 1` 单次随机采样导致 Run 1→2→3 Candidate 呈现 `0.6 -> 0.4 -> 0.3` 波动（Base 亦在 `0.4 -> 0.4 -> 0.5` 波动）。

### 5.2 Stage 4 下阶段演进规划

1. **按单步上下文压力触发真正长程 DTOC（关闭短会话无益卸载）：**
