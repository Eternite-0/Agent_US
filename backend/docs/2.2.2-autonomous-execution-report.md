## 3. Memory Trust 与 Capability Persistence

### 已实现

- 普通 Memory API 的 `verified:true` 不会授予可信验证状态。
- 普通反馈接口不能使用 `verify` 或伪造 Evaluation evidence。
- Trusted verification 需要私有服务端 authority、项目匹配、已完成 synthetic Evaluation Run、任务证据和完整评分。
- Capability Registry 将 declared 与 measured 分离，并通过 Store 持久化、重启恢复。
- measured capability 不能通过通用 API 写入，必须关联 Evaluation Run、evidence references 和可核验任务结果。
- Evaluation 完成后，所有已判定的 passed/failed task evidence 都可进入 capability measurement 聚合；取消/超时不会被伪装成成功。
- Experience Memory 已接入 ContextAssembler 的项目范围检索和 token budget。

### 已测试

- Memory trust negative tests：通过。
- Capability trust negative tests：通过。
- Store reopen / startup restore：通过。

### 尚未完成

普通 DirectAgent/Swarm 生产任务的自动 Memory Candidate 提取、脱敏、人工/独立 verifier 审查和最终写回尚未形成完整闭环；当前可信自动写回主要由确定性 Evaluation 结果驱动。

## 4. Durable Evaluation

### 已实现

- 保留 30 个确定性 Smoke Benchmark task。
- 新增独立 `agent-us-real-engineering` Benchmark，包含 10 个任务定义：
  - 多文件功能开发
  - Bug 修复
  - 陌生代码库分析
  - 多模块重构
  - 单元测试补充
  - API 兼容性修改
  - 安全审计
  - 数据处理
  - 中断恢复
  - 多 Agent 并行开发
- 每次 Evaluation 使用临时 workspace；需要时初始化 Git baseline 并收集 diff。
- 持久化 Evaluation Run、Task、Attempt、Checkpoint、Artifact、Budget、Judgement。
- Runner 支持 timeout/cancel、runtime drain；无法确认 runtime 已停止时不删除 workspace。
- RecoveryWorker handler 支持跨 Node 进程恢复。
- 恢复时从 durable task result 重建 run.results/score；已通过任务不重复执行；已有 attempt offset 与剩余 attempts 共同限制总 attempt 数量。
- 确定性 Judge 失败不会被模型辅助结果覆盖。

### 真实边界

当前跨进程恢复测试通过“预置 running durable rows 后由新 Node 进程恢复”，它不是 Evaluation 运行中的真实 SIGKILL 故障注入。已有 Swarm/Direct Runtime 的真实崩溃恢复测试不应被错误标称为 Evaluation SIGKILL 证据。

## 6. Adaptive Planner 与 Swarm 集成

### 已实现/已集成

- `AdaptiveSwarmOrchestrator` 的 planning job 可调用现有 DynamicTaskPlanner 形成 DAG。
- 结构化 Planner plan 经过 schema/DAG/权限/预算校验后进入既有 durable Swarm。
- `TeamOptimizer` 在 dependency resolve / dispatch 阶段实际参与单 Agent 与 team 选择。
- selected model/provider 写入 `swarm_nodes`，并生成既有 `swarm_node_execute` durable jobs。
- measured capability 可作为 candidate effective capability 进入路由和 team scoring。
- 简单任务优先单 Agent；多独立 workstream、高风险或独立验证任务才允许 team mode。
- 旧节点重规划时保留已执行副作用、artifact、receipt 和 model assignment。

### 尚未完成

- 普通 DirectAgent 输入不会自动将所有请求升级为 Planner → TeamOptimizer → Swarm；当前稳定入口是显式 Planner/Swarm API 和 Swarm planning job。这是有意避免改变普通聊天语义的边界。
- TeamOptimizer 返回的 reviewer 选择尚未在所有路径中自动物化为独立 Reviewer Swarm node；结果冲突仍依赖现有 verifier/aggregator 语义。

## 7. Unified Agent Communication

### 已实现

- CommunicationBus 使用持久化 Store adapter、envelope schema、至少一次投递、delivery token、ACK、retry、过期和 dead-letter。
- Store 与 Memory adapter 的 runId 过滤、幂等作用域和 stream ordering 保持一致。
- Swarm dispatch 可通过统一 Bus claim 与子 Agent 节点关联；legacy `agent_messages` 路径仍保留兼容。
- Legacy mailbox 继续可用于无 conversationId 的历史调用方，不被直接删除。
- 双 Runtime claim/ACK 测试证明同一消息不能同时获得两个有效 delivery lease。

### 语义边界

Unified Bus 的 claim 与 child turn persistence/ACK 仍是 at-least-once 的跨事务桥接，不宣称 exactly-once。后续应将 message binding/fence 进一步持久化到 child turn，并补充“child turn commit 后 ACK 前崩溃”的故障注入测试。
