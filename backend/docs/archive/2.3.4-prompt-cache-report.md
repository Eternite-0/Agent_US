# Agent_US 2.3.4 — Prompt Cache Intelligence 验证报告

## 结论

真实 WorkBuddy 样本确认了缓存遥测可以读取、加权和按模型分组；**没有证据表明本次改动显著提高了整体命中率或降低了实际账单**。五个可比较场景中，三个全程命中率下降，一个持平，一个上升但请求多了一次。代码修改场景候选组未完成，不计为性能对比成功。

## 实现与统计口径

- 在现有 `MetricsCollector` 中通过 `runtime_metrics_events` 记录 `provider_usage`；不新增数据库表。每次 Agent Provider 请求有一个独立 ID，流式用量按累计快照更新；在下一次读流之前保存已观测用量，再更新结果。故障切换、推理重试和任务恢复发起的新请求有各自的记录，不重放旧记录。进程突然退出时，记录可能停留在 `streaming`，仍保留已收到的快照；上游未发送的 Token 无法恢复。
- 总输入：OpenAI 兼容使用 `prompt_tokens`，不重复加回缓存；DeepSeek 可用 `prompt_cache_hit_tokens + prompt_cache_miss_tokens` 补充缺失的总输入；Anthropic 使用 `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`。缺字段不会变成零命中。缓存写入量只累加明确报告值，不能由读取量或未命中量反推。
- `GET /v1/observability/metrics?view=prompt-cache&windowHours=24` 默认排除测试流量，返回全局、Provider、wire model 三组统计。读取量、可统计输入量、未命中量使用有完整命中率口径的请求；命中率为 `sum(read) / sum(eligible)`。创建也是本次未从缓存读取的输入；它不能再与未命中量相加来求总输入。覆盖率为有完整口径的请求占比，不是有命中的请求占比。显式零命中显示 `0%`；没有可用分母显示 `—`。已知不支持与缺字段分别保留计数。旧的 `averageTokenUsage.cacheReadRatio` 保留标记为 `legacy` 的回退，Composer 不使用旧估算。
- Status Bar 参考 DeepSeek Harness 提交 `4b399c39a6d1479cd84ca591b4d7c88e24d38a96` 的 `packages/client/ui-chat/src/client/chat/StatsPills.tsx` / `StatsPills.module.css`。主页和聊天共用 Composer；终态事件后刷新，30 秒轮询兜底。不展示 Benchmark 模拟会话的数据。
- 沿用同会话静态系统提示词、Session Nonce、持久化历史尾注和已有压缩器。将 Provider 工具 Schema 序列化固定化，由 Runtime 自有尾注判断上下文是否重复，优先从较晚的可剪裁工具结果减量；Anthropic 标记系统及最近内容边界。原生 OpenAI 才添加会话隔离的 `prompt_cache_key`。Provider/账号健康且 wire model 相符时优先复用会话路由；出错仍可故障切换。权限、工具集、摘要替换等真正改变输入的操作仍可能让相关前缀失效；首次启用规范化工具排序也可能需要重新热身。
- 目前缓存统计覆盖 Direct / Swarm / Agent Provider Adapter 调用。面向外部客户端的透明反向代理只保留/转换响应里的用量，未计入 Composer；无 Agent 会话的外部调用也没有 `sessionId`/`turnId`。`inputTokens` 在 Agent_US 记账中是总输入，不沿用 Harness 展示组件的 uncached-input 字段约定。

- WorkBuddy 样本的缓存统计覆盖率为 100%，缓存写入字段报告 `0`。未获得适用费率或计费记录，**实际金额未知**；表中总 Token 是用量而非价格。平均请求延迟从发出请求至响应流结束，不含用户批准耗时。
- 首次请求的读缓存差异尤其显著：普通对话 `2,816 → 512`，长上下文与压缩均 `3,456 → 512`。只看首请求之后的诊断口径（不替代全程数据），普通对话 `94.67% → 94.50%`，长上下文 `97.06% → 95.52%`，压缩 `92.31% → 93.38%`。可能有网关冷热、既有缓存、工具 Schema 首次变化以及模型输出差异等因素，不能只靠本次数据识别因果。
- 候选组代码修改没有写出预期文件：一轮没有工具回执、一轮有一个回执，均超过等待窗口并被取消。不得以更少的 Token 当作节省。Swarm 虽有较高命中率，但更多的请求使总 Token 增加。
- Anthropic、OpenAI 的分母、取消后部分用量、跨协议 failover、重试去重有本地回归；没有 Anthropic 和原生 OpenAI 的真实收费基准。下一次应 pin 到可验证的网关上游账号、对各场景做交错 A/B，分别记录首次请求和稳态，重复执行并以验证通过的工作负载对比。实际成本需网关账单或确认适用的计费表。

### 复现

安装基线和候选各自的 backend 依赖后，从候选 worktree 根目录执行；凭据仅通过环境变量提供，不写入报告、命令历史或仓库。脚本运行真实有用量的请求，只输出数值和场景状态。参数可分别选择 `plain edits long tools compact swarm`，省略则运行全部。脚本会验证压缩是否激活、修改结果是否落盘，并在候选工作负载未完成时返回非零。

```sh
export CACHE_BENCH_ENDPOINT=http://127.0.0.1:7863/v1
export CACHE_BENCH_MODEL=cn:deepseek-v4.1-flash
# 使用本机秘密管理方式设置 CACHE_BENCH_KEY 后再运行：
CACHE_BENCH_SOURCE=/path/to/baseline node backend/scripts/prompt-cache-benchmark.mjs > before.json
node backend/scripts/prompt-cache-benchmark.mjs > after.json
```

`CACHE_BENCH_PROTOCOL=anthropic` 可切换 wire 协议；因此也需要一个实测账号和对应模型。建议以单场景执行，便于交错顺序和重跑；不要将 benchmark 的非零状态当成“真实缓存不支持”。

## 工程验证

运行后端全量与相关回归，并在同主机对 GitHub 基线重跑失败用例。系统没有 Docker/Magpie 运行资源；未改动 Benchmark Sandbox 安全隔离模块。Ubuntu 和 Windows 使用仓库既有 Node 24 CI 矩阵，构建状态以对应候选提交的 GitHub Actions 记录为准。
