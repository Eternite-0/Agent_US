# Agent_US 2.3.5 — Tool Intelligence 验收报告

- 基线：`4d0e4870fc1aeb9f1ed18b9756ba8bc88c3b0bdb`；实现分支：`codex/tool-intelligence`。
- 实测环境：macOS x64、Node.js 24.14.0；使用隔离临时工作区和新建 SQLite。未读取运行中的账户或凭据。
- 范围：直连流式推理、工具分发与取证、Workspace Tools、MCP。没有修改静态系统提示、Prompt Cache、ContextAssembler、缓存统计、旧 DAG 要求或审批/沙箱授权规则。

## 1. 审计结论与取舍

| 链路 | 基线代码与实测信号 | 本轮处理 |
|---|---|---|
| AgentLoop → EvidenceVerifier | `node --test` 已失败，随后 `git status` 成功；整个回合却通过，独立测试仍失败。Verifier 只看最后一个 shell 回执是否成功。 | 将回执与实际执行参数关联，常见独立验证命令按会话、目录、命令跟踪。同一检查重跑成功才能覆盖早期失败；无关命令不能。直连修复消息精确指向失败调用。 |
| Dispatcher → Shell / MCP → Tool Receipt | Dispatcher 从自由文本匹配 `exitCode:`；MCP 成功返回的历史日志可被判成失败，真实 `isError: true` 可被判成成功。 | 由注册的执行器报告结构化状态；stdout、进程日志和 MCP 内容都不是执行状态。MCP 响应丢失进入 `outcome_unknown`，不重试，复用既有人工核对门。 |
| MCP 发现 | 启动/枚举按服务器串行；只读第一页，备用能力不可见。 | 每次发现最多四路独立服务；处理游标，有时间、页数、工具数和重复游标限制。损坏服务降级，不挡其他服务；当前已发现目录中的歧义别名不对模型开放。 |
| 工具调度、错误恢复 | 连续读调用无并发上限；致命异常可先使批次退出，其他读仍在飞。防循环比较参数原串。 | 仅将明确只读、可重放、非外发的操作放入最多四路读阶段；保持写/外部操作顺序以及结果原顺序。致命异常停止接纳并等已启动读取收尾。参数规范化后识别重复；只有明确仍在运行的状态轮询可免于重复计数，步数/时间预算仍适用。 |
| 工具选择、组合、Skills | 检查了 `ToolRegistry`、Workspace Tools 元数据、`discoverMemoryAndSkills` 与 task skill pinning 路径。基准的直接故障集中在验证和 MCP，而不是新任务规划架构或技能装载。 | 补充仓库侦察、按路径/文本定位、先读再编辑、多文件补丁、单独运行验证的工具描述；不另造计划 DSL、自动执行策略或扩大 Skill 可读取范围。 |
| 权限、审批、幂等性 | 分发仍经过参数校验/钩子重校验、实时策略、审批摘要、单次 ExecutePermit、租约围栏与持久化回执。 | 不按命令字符串猜测只读，不并行化写入或 MCP 调用，不自动重放未知效果。脚本/测试用审批与真实回执验证这条路径。 |

## 2. 工程任务基准及验收方式

用同一脚本测试两个版本。确定性 provider adapter 只提供模型侧决策：在初次误报通过后，必须看到运行时修复反馈，才会根据真实源码、测试和失败输出来编辑、复测。模型返回的文本不参与外部真值判断。运行的 AgentLoop、文件工具、Git、Node 测试、审批、SQLite 回执、stdio MCP 及完成门均为实际实现。未使用外部付费模型；结果不能当作跨模型的自主规划提升。

1. **修复计费模块。** 通过 `glob` / `read_file` 取证，运行现有失败测试及独立 Git 诊断，审批后局部修复并重跑原命令。外部验收用全新的 Node 测试进程，并逐字节比对原测试文件，要求源码已修复且运行时正确验收。
2. **MCP 调查与回退。** 三个真实 stdio 子进程。一个展示第二页能力，且先返回包含 `exitCode: 9` 的正常日志，再报告应用错误。按真实工具结果选择第二页的备用查询，并对日志、错误、回退分别验证回执。
3. **并发资源压力。** 12 个独立异步真实文件读取、一个写屏障、一个后续读取。验证结果原顺序以及读写可见性；记录峰值与墙钟。每个读取有固定 8 ms 模拟服务时间，不是仓库扫描吞吐测试。

每个版本独立运行 7 次；下表为墙钟中位数（毫秒），括号内是最小–最大值。样本小，时间有抖动，不承诺生产 SLA。

| 指标 | 基线 | 2.3.5 |
|---|---:|---:|
| 计费任务：实际修复且独立测试通过 | 0/7 | **7/7** |
| 计费任务：运行时误验收 | 7/7 | **0/7** |
| 计费任务：推理步数／显式审批次数 | 3／2 | 5／4 |
| 计费任务：回合耗时 | 886（627–1,903） | 2,833（966–5,780） |
| MCP：正确识别正常日志、失败和回退 | 0/7 | **7/7** |
| MCP：发现耗时 | 829（659–1,081） | **476**（416–1,419） |
| 并发：读写屏障及结果顺序正确 | 7/7 | 7/7 |
| 并发：峰值读取数／批次耗时 | 12／21（18–445） | 4／48（38–198） |

MCP 发现中位数减少约 **43%**，同时实际读取了更多目录页。计费任务耗时增加是因为现在完成了原本被漏掉的修改和复测；不能把错误的基线“提前完成”当作等价的性能基线。读批次主动以一定延迟换取资源上限，没有宣称提速。

**执行记录（各次状态一致）：**

- 计费：基线 `test-initial failed/1 → diagnostic finished/0 → verifier pass → 独立测试 1`；升级 `test-initial failed/1 → diagnostic finished/0 → verifier fail → fix finished/0 → test-final finished/0 → verifier pass → 独立测试 0`。
- MCP：基线 `log failed/NON_ZERO_EXIT → index finished → 无备用项`；升级 `log finished → index failed/MCP_TOOL_ERROR → lookup_index finished`。第二页回退仍执行独立显式审批。

## 3. 回归与发布边界

- `npm run check`、前端 `npx tsc --noEmit && npm run build`、桌面 `node --check desktop/main.mjs` 均通过；前端仅报告构建 chunk 体积警告。
- 定向回归 **31/31**（包括审批摘要/消耗、钩子、命令分析、沙箱、Verifier、MCP 与 4 项新增回归）。新增测试断言：读车道上限及排空、状态轮询与参数顺序、分页死循环隔离及丢失响应后的核对、同目录复测才解除失败证据。
- 后端全量 `--test-concurrency=4`：**357 项，349 通过、8 失败**。将这 8 项在基线和升级分支各自串行复测，两个版本均为 **3 通过、5 失败**。三项串行通过的是 CPU 限制用例、JudgmentService 本地 HTTP 用例和 Cron DST 耗时用例；仍失败的是三项 Docker 集成（本机 `docker` CLI 不可用）和两项 Magpie 集成（`MAGPIE_UNAVAILABLE`／provider 未就绪）。因此不宣称全量绿灯或容器/真实提供商验收。

未扩大权限、降低断言或更改隔离套件来换取通过率。验证收紧专注于可识别的独立命令和当前执行链路可关联的有效参数；没有证明任意脚本、异步任务启动、混合或复合命令就是成功证据。未新增用于跨重启恢复命令语义的字段，孤立旧回执仍由既有规则核对。没有做 Windows 原生或外部模型供应商实跑，不能把 macOS 的结果外推成这两类环境的验收结论。

## 4. 复现

在当前分支工作区运行（两个工作区的 `backend/` 均需准备各自 lockfile 对应的 Node 依赖）：

```sh
git worktree add --detach /tmp/agent-us-ti-baseline 4d0e4870fc1aeb9f1ed18b9756ba8bc88c3b0bdb
node backend/scripts/benchmark-tool-intelligence.mjs /tmp/agent-us-ti-baseline/backend 7 > baseline.json
TI_REQUIRE_PASS=1 node backend/scripts/benchmark-tool-intelligence.mjs "$PWD/backend" 7 > upgraded.json
(cd backend && npm run check)
(cd backend && node --test --test-concurrency=4)
(cd frontend && npx tsc --noEmit && npm run build)
node --check desktop/main.mjs
```
